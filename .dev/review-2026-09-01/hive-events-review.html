Design review · 2026-09-01 · hive-events 0.5.9 · hive-event-protocols 0.1.1

Is hive-events still worth keeping?

Yes, as the in-process kernel it already is: an interceptor chain, an effects and coeffects registry, a deterministic FSM with halt and resume, and an observer seam. Fifteen fleet repos call it, and hive-mcp's workflows, hive-agent's lifecycle and hive-workflows' progress stream run on its FSM and registries. No, as the "async event system with sagas" the README describes: the saga bus hears no dispatch, async handlers fail, the whole async namespace has no consumer anywhere, and the wire-protocol sibling never runs under the engine. The library has not fallen behind; it has been carrying claims it does not meet, and three copies of its own dispatch loop.

Keep, it earns its place
  • interceptor, fx, cofx: the re-frame kernel, small and correct
  • fsm: compile, run, halt/resume, sub-FSM effect capture
  • observer: the one open seam, added 0.5.4
  • multi's pure orchestration half (validate, waves)
Fix before building on it
  • Three registries, one dispatch contract
  • Saga/pub-sub fed from dispatch, or removed
  • :async? handlers real, or removed
  • hive-event-protocols specs ported to the engine's shape
Do not build on, as it stands
  • hive.events.async/saga as a process manager
  • hive.events.async debounce and retry for anything registered outside the router
  • The README's "sagas" and "events over the wire" claims

Findings

criticalconfirmed

hive-event-protocols never runs under the engine

Six of seven transports (tcp, tls, http1, http2, http3, websocket) write their machine as {:id :initial :states {k {:enter :handle :dispatch}}}. The engine reads {:fsm {k {:handler :dispatches}}} and starts at ::fsm/start. Compilation silently yields the three privileged states and nothing else; a session throws on its first step. Only retry.clj speaks the engine's dialect, and it runs. The suite is green because every test calls handlers directly and asserts on the spec's state count; no test calls run-session. This is the Evidence Stratification attractor in its purest form: written, unit-tested, never executed.

criticalconfirmed

Three event registries in one JVM, one shared fx registry

The router (reg-event-fx), the multimethod registry (register-handler!) and hive-mcp's own (reg-event) each hold handlers, each re-implement the same handler-interceptor plus execute plus do-fx loop, and each decide differently what an unhandled event means: warn and drop, throw, throw with a boot check. All three write effects into the one global fx registry, and hive-mcp reaches into the private cofx atom by resolve. Every async helper (debounce, retry, saga) targets the router only. The result is the diagnostic that already misled one session: handler-registered? says false for an event that dispatches fine, because it asks a registry dispatch does not consult. This is a Single-Source Lever fault. The fix is one registry contract and a dispatch policy passed as data, not a fourth registry and not more cross-patching.

highconfirmed

The saga is a go-loop over a bus nothing feeds

hive.events.async keeps a private pub that only publish-event writes to. The router never publishes, so the README's saga example, reacting to :order/created and :payment/completed, reacts to nothing. The state is an in-memory map in a go-block: no correlation id, no persistence, no timeout, no compensation. It is a subscriber, not a process manager. The observer seam added in 0.5.4 is the honest replacement and one GlobalObserver would connect the bus in a line.

highconfirmed

:async? true FSM handlers do not work

run hands the handler identity as its callback and then uses the handler's return value. A handler that returns nil and calls back later transitions on nil and lands in ::error. The flag only "works" for a handler that returns the callback's result synchronously, which is not async. Either await a promise or channel from the callback, or delete the flag and the normalize shim.

highconfirmed

Three namespaces have no consumer in the fleet

A require-site sweep over every repo that pins hive-events finds no caller of hive.events.async, hive.events.log or hive.events.schema outside the library's own tests. Timeout, retry, debounce, throttle, pub/sub and saga are dead code in production, which turns the two findings above from "fix" into "delete": remove async in 0.6.0 and let hive-weave own retry and timeout, as ->timed-interceptor already does. schema is a good seam that nobody found; fold it into the router as an opt-in and document it. log is fine as plumbing.

mediumplausible

Unhandled events are a policy, and the library picked the worst one

The router warns and returns nil; nothing is retried, counted or surfaced. The loud-fail work (ENGINE-L0.4) shipped as verify-handlers! in hive-mcp, so only hive-mcp's registry has a boot check. Library users still get the warn-and-drop that absorbed a retry storm once. Under a unified registry the policy becomes an injected strategy: {:on-unhandled :warn | :throw | :dead-letter}.

mediumplausible

Backpressure is an assertion error

dispatch does put! on a 1024-buffer channel. Past the buffer, core.async queues pending puts up to 1024 more, then throws. A burst of unprocessed events crashes the emitter instead of blocking or dropping by policy. :dispatch-later spawns a future per delayed event. Neither matters in-process today; both matter the moment events cross a process boundary.

lowconfirmed

Effect order is undefined, except :db

do-fx iterates a map; only the FSM's do-fx-seq preserves order. A handler that returns {:dispatch ... :log ...} cannot rely on the log landing first. The FSM already has the ordered form; the router should accept a vector of pairs as well and document the map form as unordered.

lowconfirmed

hive.events.multi is two libraries in one file

The top half is a handler registry with interceptors; the bottom half is a pure DAG compiler (normalize, validate with Kahn, batch fan-out, waves) that exists for hive-mcp's multi tool and has nothing to do with events. The compiler is good code and well tested, which is the argument for moving it to its own namespace, not for leaving it here.

Seams for a microservices shape

Today an event never leaves the JVM through hive-events. hive-mcp publishes spawn and kill to NATS through its own bridge, outside the bus; hive-cache invalidates through the observer; hive-event-protocols is a set of wire-level connection FSMs (TCP handshake, TLS, HTTP framing), not an event transport, and it is not runnable. So the answer to "should we build seams" is yes, but small, and in a specific order, because most of what a distributed bus needs is missing at the data level before it is missing at the transport level.

What exists that a seam can stand on

  • IEventObserver: a clean, isolated tap after effects. An outbox writer is one observer.
  • fsm halt/resume: a state machine can be parked as data and resumed later, which is the core of a durable process.
  • hive.events.schema: payload coercion against a registered malli key, already lazy and platform-safe.
  • IProtocolFSM and ITransport in hive-event-protocols: the right idea, wrong layer for events; keep them for connections.

What is missing, in dependency order

  1. Envelope. A malli Event value object: event-id (uuid), type, payload, occurred-at, correlation-id, causation-id, source, version. The vector form [type payload] stays as the in-process projection of it; nothing crosses a boundary without the envelope.
  2. Transport port. IEventTransport with publish!, subscribe!, ack!, close!, provider behaviour as data (at-most-once, at-least-once, ordering, max payload), exactly the profile-in-registry pattern from the clj-subsystem canon. The in-memory transport is the reference implementation and the test double. NATS JetStream is a separate leaf lib, never a hive-events dependency.
  3. Outbox and inbox. An observer that appends published envelopes to an outbox port; a subscriber that checks an inbox port by event-id before dispatching. Idempotent consumers are a policy on the unified dispatch, not a convention in every handler.
  4. Dead letters. The unhandled and failed-handler policy routes to a dead-letter port instead of stderr.

None of these need a broker to be designed or tested. All of them need the single registry first, or the outbox observer will fire for the router and stay silent for hive-agent's events.

Sagas, if the word is going to mean something

A saga in the Garcia-Molina sense is a sequence of local transactions with a compensating transaction per step; a process manager is the routing state that drives it from events. hive-events has the pieces for the second and none of the first. The honest design is an FSM per saga instance, keyed by correlation id, whose handlers return {:data :fx} where the fx are commands to other services and where every forward step registers its compensation as data in the FSM's state. Timeouts are ::halt plus a scheduled resume; failures transition to a compensating branch that replays the registered compensations in reverse as ordered effects through do-fx-seq. Persistence is a port (ISagaStore: load, save, list-pending), and the trigger is the observer feeding an event whose correlation id matches a parked instance.

That is a new namespace, hive.events.saga, built on fsm, observer and the envelope, with the store injected. It replaces hive.events.async/saga, which should be deleted rather than repaired. It also gives hive-workflows and the payment work a shared spine for the multi-service flows they are already sketching by hand.

Recommended order

  1. 0.6.0, honesty release. One registry contract with dispatch policy as data; router and multi become two registrations of it (or multi's registry is deleted and hive-agent's emit! moves to the router with per-event interceptors it already supports). handler-registered? answers for the registry dispatch uses. Delete hive.events.async (no consumers) and the :async? flag. Public unreg-fx / unreg-cofx already exist, so hive-mcp's private-atom reach becomes a call. do-fx accepts ordered pairs. Move the multi-op compiler to hive.events.plan. README rewritten to the measured surface.
  2. hive-event-protocols 0.2.0. Port six specs to the engine's dialect, one run-session test per transport. Until then, retag the fleet index so nothing routes to it for "events over the wire".
  3. 0.7.0, envelope and transport port. Malli Event envelope, IEventTransport with an in-memory reference, outbox and inbox observers over injected ports, dead-letter policy. hive-mcp's NATS bridge becomes the first external adapter, in hive-mcp.
  4. 0.8.0, saga on the FSM. hive.events.saga: correlation-keyed FSM instances, compensations as state, halt-based timeouts, ISagaStore. First consumer: the payment settlement flow already on the board.

Each step is a card or a card to be cut. Steps 1 and 2 are on the board now; 3 and 4 are gated on 1 and are proposals until the registry lands.

Two things the sweep settles. The FSM is the load-bearing half of the library: twenty of hive-mcp's forty-one sites and every workflow spec are FSM graphs, which is why the halt/resume asset matters more than the router. And the fleet already wrote the adapters the library lacks: hive-agent's composition over register-handler!, hive-system's journal interceptor, hive-workflows' NATS transport, hive-carto's correlation ids. The 0.7.0 seams are mostly a matter of pulling those four back into one place.

hive-universe's weight test is a design signal on its own: SCI is a hard dependency carried for EDN predicate evaluation in fsm/compile, and every consumer pays for it. Resolving SCI lazily, the way hive-weave and hive-spi already are, would let the kernel stay on core.async alone.
